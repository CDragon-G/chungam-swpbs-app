# 0.26.0 출시노트

K-ODR 기록을 CICO(Tier 2)와 학생맞춤통합지원(Tier 3)으로 바로 잇습니다.
학교가 많아져도 버티도록 서버에 몰리던 부분을 덜어냈습니다.

## 배포 순서

```
1. 059_kodr_tiered_support.sql    앱 배포 전에 (구버전에도 알림·자동 상정은 바로 동작)
2. 061_bottleneck_relief.sql      앱 배포 전에 (0.26.0 대시보드가 이 함수를 부릅니다)
3. 0.26.0 을 스토어에 올리고 출시 완료까지 기다린다
4. 버전 게이트 올리기              ← 출시가 끝난 뒤에만
```

**061 은 반드시 앱보다 먼저.** 0.26.0 의 교사 홈·대시보드는 061 에서 만드는
서버 함수로 숫자를 받습니다. 061 없이 0.26.0 이 깔리면 대시보드가 비어 보입니다.
구버전 앱은 061 이 있어도 그대로 동작하고, 학교 새싹·명예 식집사는 바로 가벼워집니다.

**059 는 앱 업데이트 없이 바로 효과가 납니다.** 기준 판정은 K-ODR 이 저장되는 순간
서버에서 일어나므로, 지금 쓰는 앱으로 K-ODR 을 적어도 관리자 선생님께 알림이 가고
학맞통 안건이 만들어집니다. 안건을 **보고 관리하는 화면**은 0.26.0 부터 있습니다.

**이미 기준을 넘은 학생은 자동으로 올라가지 않습니다.** 판정은 새 K-ODR 이 저장될 때
일어나기 때문입니다. 0.26.0 을 설치한 뒤 관리자 계정으로 앱에서 한 번 눌러 주세요.

## 선생님께 (스토어에 올리지 않는 내용)

### 흐름

```
K-ODR 저장 ─→ 최근 30일 · 학년도 누적 건수를 센다
              ├─ 최근 30일 3건 이상         → 🔔 CICO 권장 알림 (이미 CICO 중이면 생략)
              └─ 최근 30일 5건 이상
                 또는 학년도 누적 7건 이상  → 🧩 학맞통 안건 자동 상정 + 알림
```

알림은 **관리자(리더십팀) 선생님**께 갑니다. 같은 학생에게 기간 안에 두 번 알리지 않고,
한 학생에게 열린 안건은 하나뿐입니다.

### 기준값의 근거

흔히 인용되는 PBIS(SWIS) 기준은 **한 해** 동안 0~1건이면 Tier 1, 2~5건이면 Tier 2,
6건 이상이면 Tier 3 입니다.

학년도 누적만 보면 한 달에 몰려 생긴 위기를 늦게 알아차리고, 최근 30일만 보면 한 달에
1~2건씩 꾸준히 이어지는 학생을 놓칩니다. 그래서 학맞통은 **두 창을 함께** 봅니다.

| | 기본값 | 조정 범위 |
|---|---|---|
| 살펴볼 기간 | 30일 | 7~90일 |
| CICO 권장 | 3건 | 1~10건 |
| 학맞통 안건 (최근 기간) | 5건 | 2~20건 |
| 학맞통 안건 (학년도 누적) | 7건 | 0(끔)~60건 |

학맞통 기준은 CICO 기준보다 커야 저장됩니다.

**이번에 바로잡은 것.** 기존 CICO 화면에 "연구에서는 **월** 2~5건을 Tier 2 검토 기준으로
권장" 이라고 적혀 있었는데, SWIS 기준은 **한 해** 기준입니다. 교육청 단위로 보급되면
담당자들이 근거를 확인할 수 있어 문구를 고쳤습니다.

### CICO 후보 목록이 달라집니다

지금까지는 **"이달"** 기준이라 매달 1일이면 0건으로 초기화됐습니다. 9월 30일에
3건이던 학생이 10월 1일 목록에서 사라졌습니다. **최근 30일** 로 바꿨습니다.

(K-ODR 화면의 월별 요약 탭은 달력 한 달을 보는 보고서라 그대로 "이달" 기준입니다.)

### 학맞통 연계 안건 화면

**대시보드 → 학맞통 연계 안건** (관리자에게만 보입니다)

- 안건마다: 최근·누적 K-ODR 건수, "개입 필요" 표시 건수, 자주 일어난 장소·행동 상위 3개,
  CICO 이력, 마지막 기록일
- 진행 상태: 안건 상정 대기 → 회의 예정 → 학맞통 지원 중 / 관찰 유지 → 종결
- 회의 날짜 지정
- 학교별 기준 조정 · "지금 기준으로 전교생 다시 확인"

**K-ODR → 월별 요약** 에서 학생마다 **"학맞통 안건으로 올리기"** 버튼이 있습니다(관리자).
기준에 닿지 않았더라도 한 번의 심각한 사건처럼 리더십팀이 판단한 경우에 씁니다.

### 개인정보 — 일부러 넣지 않은 것

학맞통 대상 여부는 매우 민감한 정보입니다.

- **안건 목록은 관리자 선생님만** 봅니다. 표를 직접 읽을 수 없고 서버 함수로만 열립니다
- **알림 문구에 학생 이름을 넣지 않습니다.** "2학년 3반 학생 1명이 기준에 닿았어요"
  처럼만 적습니다. 알림은 잠금화면에 뜰 수 있습니다
- **회의 내용(자유 서술)은 앱에 저장하지 않습니다.** 상태와 회의 날짜만 둡니다.
  회의록은 학교의 학맞통 공식 기록에 남기는 것이 맞습니다

### 선생님이 적은 K-ODR 은 반드시 저장됩니다

판정이나 알림 단계에서 어떤 오류가 나도 K-ODR 기록 자체는 저장되도록 했습니다.
같은 학생의 K-ODR 두 건이 동시에 저장돼도 안건이 중복되거나 저장이 실패하지 않습니다.

### 확인용

```sql
select name, kodr_window_days, kodr_cico_threshold,
       kodr_tier3_threshold, kodr_tier3_year_threshold
  from schools where id = '<우리 학교 id>';

select status, count(*) from support_referrals
 where school_id = '<우리 학교 id>' group by status;
```

## 서버 부담 줄이기 (061)

서울 전체로 넓어졌을 때 먼저 막힐 곳을 찾아 고쳤습니다.

| 어디 | 전에는 | 이제는 |
|---|---|---|
| 교사 홈 · 대시보드 | 전교 14일치 점검 원본(문항별 O/X 포함)을 통째로 내려받아 앱에서 계산. 1,500명 학교면 여는 순간마다 약 1만 건 | 서버가 합계만 계산해 수 KB 로 보냄 |
| 반별 통계 | 반 하나를 열 때도 전교 14일치를 다시 내려받음 | 그 반 것만 서버에서 합침 |
| 학교 새싹 | 누가 앱을 열 때마다 20여 가지를 새로 셈 | 학교별로 10분 동안 결과를 보관 |
| 이 주의 명예 식집사 | 홈을 열어둔 학생마다 5분마다 전교 순위를 새로 계산 | 학교별로 5분 동안 순위를 보관 |
| 학생 '총 점검 횟수' | 지금까지의 점검 id 를 전부 내려받아 셈 | 숫자 하나만 받음 |
| 학생 60일 기록 | 내 기록 화면과 뱃지가 같은 기록을 두 번 내려받음 | 한 번 받아 나눠 씀 |
| 점검 알림 | 전교생 17:00 정각 | 기기마다 17:00~17:29 로 흩어짐 |

**보관해 둔 값이 만료되는 순간** 여러 명이 동시에 들어와도 한 명만 다시 계산하고
나머지는 직전 값을 받습니다. 한꺼번에 몰려 서버가 멈추지 않게 하기 위해서입니다.

**달라 보일 수 있는 것**

- 학교 새싹 점수와 명예 식집사는 **최대 10분 · 5분 늦게** 반영됩니다. 점검 직후
  "내 점수" 가 바로 오르지 않을 수 있습니다. 5분 안에 반영됩니다.
- 대시보드의 전체 학생 수와 참여율에서 **졸업·전출 처리된 학생이 빠집니다.**
  전에는 섞여 있어 참여율이 실제보다 낮게 나왔습니다.
- **총 점검 횟수가 학기 정리 후에도 이어집니다.** 060 으로 1학기 원본을 정리하면
  횟수가 0 부터 다시 시작하던 문제를 함께 고쳤습니다 (뱃지 기준도 같음).
- **알림 시각:** 기본값 17:00 그대로이거나 오전으로 맞춰 13:00 으로 올라간 학생만
  기기마다 0~29분 뒤로 옮깁니다. 학생이 직접 고른 다른 시각은 그대로 둡니다.

**Supabase 대시보드에서 한 가지 (코드로 못 하는 부분)**

학교에서는 학생 수백 명이 **같은 공인 IP** 로 나갑니다. 로그인 제한이 IP 기준이라
첫 시간에 반 전체가 동시에 로그인하면 일부가 막힐 수 있습니다.

```
Authentication → Rate Limits
  Sign-ups and sign-ins    : 지금 값을 확인하고, 한 학교 한 학년이 몇 분 안에
                             동시에 로그인해도 막히지 않게 올리기
  Token refreshes          : 같은 기준으로 올리기
```

기본값은 일반 앱 기준(한 IP 에 사람 한 명)이라 학교 환경에서는 낮을 수 있습니다. 교육청 단위 보급 전에 Supabase 에
학교 NAT 환경을 설명하고 권장값을 받아두는 것이 안전합니다.

**확인용**

```sql
select count(*) from school_growth_cache;          -- 앱을 연 학교 수만큼 생긴다
select school_id, week_start, computed_at, jsonb_array_length(ranks)
  from weekly_honor_cache order by computed_at desc limit 5;
```

# 웹사이트 (jaram-web)

### 학맞통 연계 섹션

- Tier 1 보편 지원 → Tier 2 CICO → Tier 3 학맞통, 각 기준과 자람이 하는 일
- **"Tier 1 이 튼튼할수록 Tier 3 가 줄어듭니다"** — 보편적 지원이 약한 학교와 튼튼한 학교를
  두 피라미드로 비교 (구체적인 수치는 근거가 없어 넣지 않았습니다)
- 개인정보 원칙
- 첫 화면 배지, 피라미드, 예방 흐름, 메뉴, 자주 묻는 질문에도 반영

### 최신 기능 반영

칭찬 우체통 · 이 주의 명예 식집사 · 학맞통 연계 안건 · 새 학년도 진급 처리 ·
학교 새싹 12단계와 학년도 새 출발 · 자기점검 오후 1시

### 웹 점검에서 포인트가 지급되지 않던 문제

웹 점검(student.html)은 포인트 함수를 `p_date` 라는 인자 이름으로 불렀는데 서버 함수의
인자 이름은 `p_checkin_date` 입니다. 이름이 맞지 않아 호출이 실패했고, 웹은 그 실패를
확인하지 않았습니다. **스마트폰이 없어 웹으로 점검하는 학생들이 100P 를 받지 못했을
가능성이 큽니다.**

앱과 똑같이 날짜·점수·포인트를 서버가 정하는 `submit_checkin` 으로 바꿨습니다.
점검 화면에 들어가기 전에 오늘 상태를 물어, 쉬는 날이나 오후 1시 전이면 안내를 띄웁니다.

웹으로 점검한 학생 중 포인트를 못 받은 기록이 얼마나 되는지 보시려면:

```sql
select count(*) as "포인트 없는 점검"
  from daily_checkins d
  join profiles p on p.user_id = d.user_id and p.role = 'student'
 where is_school_day(d.school_id, d.checkin_date)
   and not exists (select 1 from point_transactions t
                    where t.user_id = d.user_id and t.reason = 'checkin_daily'
                      and t.period_key = to_char(d.checkin_date, 'YYYY-MM-DD'));
```

(웹 점검과 구버전 앱 문제가 섞여 나옵니다. 소급 지급 여부는 선생님이 정하시면 됩니다.)
